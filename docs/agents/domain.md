# Domain documentation

This repository currently uses one context. Read GLOSSARY.md and relevant decisions in docs/decisions/ before proposing changes. Preserve this existing decision directory instead of creating a parallel docs/adr/ directory.

Use glossary terms consistently and identify conflicts with recorded decisions. Create terms and decisions lazily as the owner resolves them. Keep glossary entries free of implementation details, and distinguish accepted target designs from implemented behavior.

Domain documentation does not replace PROJECT.md, task and plan contracts, or docs/runbooks/agent-team.md.

## Write so the owner can understand and decide

Start documents with the main point: what we want to do, why it matters, or what the owner needs to decide. Use everyday words and explain the work as if the reader is new to it. Prefer a clear explanation over a shorter sentence full of technical terms.

Use technical names when they help, and explain them on first use. Give a small example when it makes a choice easier to understand. Keep commands, paths and other exact details accurate; place long technical details after the explanation or in a linked reference.

Write for an adult who is learning. Do not try to sound impressive. Clearly separate what exists, what we propose, and what the owner has decided. These rules apply to roadmaps, decision records, plans and GitHub issues, including Wayfinder maps and their linked questions.
